# mh3sp-rs roadmap

A from-scratch Rust server for *Monster Hunter Tri* (Wii) online play, replacing
[MH3SP](https://github.com/sepalani/MH3SP) (Python) in one big-bang migration. MH3SP is the **reference, not the
target**: we aim to do better than it, not to copy it.

This file: where the project stands, how it compares with MH3SP, what is left and in which order (updated
2026-10-09). The lasting part (reference policy, facts about the game, the numbered architecture decisions, testing,
traps): [`architecture.md`](architecture.md). Each milestone has its own file; pending console sessions:
[`recordings.md`](recordings.md).

## Against MH3SP

**At parity:** login, the world, cities, quests, chat, friends, content (byte-identical quests), announcements.

**Ahead:**
- **NAT negotiation and relay built in.** MH3SP needs AltWFC's Python 2 NatNeg, which fails behind symmetric NATs
  and Docker (error 11688). We fall back to a relay, transparently.
- **Speed.** A town relay takes ~0.3 ms instead of 50–80 ms: no stalled reads, no interleaved frames, players who
  leave vanish at once (MH3SP: ~30 s).
- **Correctness MH3SP lacks:**
  - Local Info shows the real population.
  - Seats are held by one player and freed.
  - Player Search pages work.
  - Jumps work: Change Gates, and "Warp to" from a found player or a friend, on the same world server or another
    (MH3SP's paths make every jump fail on the console, M5 D11). Seen on consoles.
  - A gate's city list stays live (MH3SP too); players listed in the order they arrived.
  - Profile ids stay stable across restarts.
  - The hunter profile is validated, so a crafted one can't crash other consoles.
  - Friend requests and messages are stored and delivered later.
- **Operations:**
  - `mh3sp stop 5min` with in-game warnings (in hunts too) and `mh3sp announce`;
  - liveness and readiness probes, JSON and Prometheus metrics;
  - anonymous logs, one SQLite file, no Python.
- **Tests:** replays with declared divergences, scripted multi-console tests, NatNeg tests with simulated NATs.

**Behind, or not done:**
- **Bans.** MH3SP has a hard-coded list of support codes (`BANNED_ONLINE_SUPPORT_CODES`). We have none: `allowed()`
  always says yes.
- **Database choice.** MH3SP can use MySQL and spread over several processes (`cache.py` on the live branch). We
  have one process and SQLite, on purpose: it holds hundreds of players.
- **Chat logs.** The live branch keeps them; we don't (D6: moderation decides later).
- **A second event rotation for one world server** (the live branch's "whitelist"). Not taken.
- **The same gaps in both:** city search (no menu found that sends it) and `LayerTell`.
- **Japanese version.** Neither handles it (MH3SP only has the EC patcher).

## Must do: a playable public server

What stands between today and strangers playing on it, in order (the checklist: M6 below):

1. **Finish M5 on consoles**: s13–s14, the Rust checks, the hour-long session.
2. **Real-world networking**, the risks no lab run covered: another machine and network (the mixed city), a real
   Wii (legacy TLS on hardware), consoles behind home routers.
3. **The US version** (`RMHE08`): recognised at login, never played.
4. **How players get here**: a Nintendo login (AltWFC's or ours), our patch with a player guide, DNS and a public
   host. Without this nobody can connect.
5. **Bans at runtime**: without them, the first griefer means a restart and a code change.
6. **Release and operations**: the release pipeline (`1.0.0`, forward-only migrations from then on), backups, a
   deployment example.

Everything else (the website, anti-cheat, jumps) is optional for a first public server.

## Could do: standing out

From most to least visible to players:

- **The website** (M7–M8). This is the project's showcase: no MH3-era server has one.
  - **Live world:** who plays where, cities and quests filling up, at a glance.
  - **Hunter pages:** HR, weapon, armour and decorations, already parsed from the profile block. Friends, and the
    Capcom ID to share.
  - **Event calendar:** the rotation and Jhen Mohran windows, past and future, from the content files. Admins edit
    the rotation there.
  - **Social:** messages, friend requests and invites written on the site and delivered in game. Kicks by a city's
    host or a quest's leader (the game has none).
  - **Accounts and pairing:** a 6-digit code links a console to an account. Optional Discord login (where the
    community is).
  - **Moderation:** bans, flags with evidence, an audit log.
  - **Public stats:** players over time from the metrics (Prometheus/Grafana).
- **Gameplay the original never had:**
  - Joining a quest after departure (research first).
  - Blocks keeping players apart.
  - City search and Change Gates that actually jump (the "jumps" step; broken everywhere today).
- **Anti-cheat** (M9):
  - decode `NtcCheatCheck`;
  - sample memory checks for Gecko codes;
  - the profile validation already done is the first layer.
- **Reach:** the Japanese version (`RMHJ08`); our own NAS if M6 ships with AltWFC (one stack, no Python).
- **Quality:** scripted Dolphin end-to-end tests as a release check; a public "how it compares" page (latency, relay,
  fixes) for the community.

### M6 — Public release

Everything between M5 and strangers playing; ends with `1.0.0`. To draft in its own file when it starts.

- [ ] Real-world networking: the mixed city on two machines (M4), a real Wii (legacy TLS on hardware), consoles
      behind home routers.
- [ ] The US version (`RMHE08`): recognised at login, never played: one lab run.
- [ ] Bans at runtime: a `bans` table, `allowed()`'s body (architecture decision 10), `mh3sp ban <capcom id>` over the
      health port like `announce`; a banned console gets its text at login.
- [ ] **Nintendo login (NAS)**: the HTTP service consoles use before reaching Capcom's servers (`/ac`:
  `acctcreate`, `login`, `svcloc`), done by AltWFC (Python 2) or Wiimmfi today. Since our patch points discs at our
  domain (M1, D3), we must answer it: AltWFC deployed next to the server until this exists; needed in some form
  before a public release.
- [ ] **Our patch**: Riivolution XML + ISO patcher rewriting every hostname of the game to our (short) domain, plus the
  certificate; with a player guide. Prerequisite of a public release.
- [ ] DNS (the domain and its NatNeg hostnames), a host with a public IP and host networking; a deployment example
      (compose, the content folder, the secret).
- [ ] Backups of the SQLite file (`sqlite3 .backup` on a schedule, or Litestream).
- [ ] **Release pipeline** (at the first real release, `1.0.0`): a Woodpecker pipeline after the tests, triggered by a
  git tag (`v1.0.0`, checked against `crates/server/Cargo.toml`'s version), builds the image (the Dockerfile compiles
  in release) and pushes it to the Gitea registry (`git.pband.ch/experiment/mh3sp-rs`, buildx plugin, `gitea_user` /
  `gitea_token`) tagged `1`, `1.0` and `1.0.0`, and the same with the `prometheus` feature tagged `1-prometheus`,
  `1.0-prometheus` and `1.0.0-prometheus` (M5 D5). Until then the version stays `0.0.0` and nothing is published.

**Done when:** players outside the lab connect with the patch and the guide alone, a ban works without a restart,
and `1.0.0` is published.

### M7 — Website, read-only

The last steps: the server is complete without it (standalone, `access = open`). First a read-only view.
- [ ] Admin API, read-only (HTTP, authenticated, next to the health endpoints): world servers, gates, cities,
      quests with their players and states, who is online and where, hunters, health and metrics.
- [ ] The website on top of it: live view of the worlds; hunter pages (profile: HR, weapon, gear from the profile
      block; friends); anti-cheat flags with their evidence (M6); health and metrics (`/health/ready`, a `/metrics`
      endpoint: players, relay latency…). History, if wanted, in a metrics system (e.g. Prometheus + Grafana), not
      in the game database.
- [ ] Admin accounts with authentication.
- Privacy follows the logging rules: the site shows Capcom IDs and hunter names to admins (moderation needs them),
  never IP addresses; support codes are masked.
- Stack decided when M7 starts (the Gitea npm registry and the Docker image pipeline are available).

### M8 — Website, editing

- [ ] Admin API write endpoints; every admin action recorded in the audit log (who did what, when).
- [ ] Moderation: kick, ban (by Capcom ID / console), broadcast announcements.
- [ ] Settings and texts in the database: a `settings` table (`access`, `registration`), terms overrides, and the
      `texts` table `(key, language, value)` with the per-language lookup (language → `en` → code dictionary).
      Only the bodies of `text()` and `allowed()` change (decision 10): their callers stay as they are.
- [ ] Event content: quest definitions, rotation and trading post (content files since M2: the website editing them
      decides where they live then), with a rotation calendar
      including the **Jhen Mohran** event (MH3SP computes its windows in `mh/time_utils.py`) and a preview of what
      players see at a given date.
- [ ] Friends lists managed from the site (the game fetches its friend list from the server, so changes show up in
      game).
- [ ] Player accounts (`registration`) and self-service access (`access = on_register | admin`), preferred flow: a
      console that isn't allowed is refused with a message such as "Register on https://… and enter the code
      482915"; the player, signed in on the site (email + password), enters it under "add a console", which links
      that console to their account (and, with `admin`, waits for an admin's approval).
      - The code is a 6-digit one-time pairing code kept in memory (~10 minutes), pointing to the console; the
        support code itself never leaves the server. The website limits attempts per account.
      - Not by typing the support code on the site, even if the game shows it in a menu (to check): codes seen in
        screenshots or streams would let anyone claim someone else's console first. The pairing code shown by the
        server proves the person holds the console right now.
      - A first-time console has no support code at OPN yet: it goes through to LMP, gets its support code in
        `AnsLoginInfo`, and is refused right there; afterwards it is refused at OPN until registered.
      - To verify in the game first: that a refusal at LMP (`NtcShut` with a text) shows its message, and that the
        console keeps the support code it was just issued.
      - Other ideas considered: typing the support code on the site (anyone could claim someone else's console);
        sign-in with Discord (an option next to email, where the community already is).
- Until M8, only `access = open` exists in practice; `on_register` / `admin` without a website is a startup `error`.
- [ ] **Messages and friend requests from the website**: written there, stored like the game's (`messages`) and
  delivered in game the same way (once, when the recipient stands in a city).
- [ ] **Kicks from the website**: the game may have no kick for players (none found in the menus or online). The
  website knows who plays which console and who leads a city or a quest, so a city's host or a quest's leader can
  kick a player there, safely: the server drops them from the city or party with the notices the consoles expect.
- [ ] A public event calendar (the rotation and Jhen Mohran windows) and public hunter pages: what players see first.

### M9 — Anti-cheat (research)

What the server can and cannot see:

| Data | Path | Server can check? |
|---|---|---|
| Hunter profile (HR, gear, stats) | `ReqUserBinarySet`, `HunterSettings` on every layer change | **Yes**: sanity rules (HR range, valid item/equipment IDs, possible combinations) |
| Game's own cheat report | `NtcCheatCheck` (`60801000`, "send cheat check data"), sent after every layer change, currently ignored | **Yes, once decoded**: Capcom's built-in anti-cheat signal |
| Game memory | `ReqMemoryCheck` (`60810100`): the server asks for N bytes at an address | **Yes**: hash code regions to detect Gecko/AR codes; random sampling over a session |
| Town positions | `NtcLayerUserPosition`, relayed through the server | **Partly**: speed/teleport checks, once the format is decoded |
| Quest combat (moves, damage, HP) | P2P UDP between consoles | **No** in `p2p` mode. In `relay` mode the traffic passes through us, but GT2 + game messages would need decoding, and validating damage means simulating game rules |
| Quest results / rewards | Mostly local to the save | **Barely**: quest duration from circle start/end, at best |

Plan:
- [ ] Decode `NtcCheatCheck` (decomp + corpus) and log it; then act on it.
- [ ] Memory-check sampling: known-good hashes of code regions per region/version; mismatch → flag.
- [ ] Profile sanity rules.
- [ ] Moderation tooling: flags, bans by support code / Capcom ID.
- [ ] Research only: decode GT2 in relay mode, position/speed heuristics.

Limits: the client is fully under the player's control. A cheat can fake `NtcCheatCheck` and memory-check answers.
The realistic goal is to stop casual cheats (Gecko codes, edited saves) and give moderators evidence, not perfect integrity.

## Future steps (unscheduled)

- **Joining a quest after it started**, as the newer games allow: Tri marks a departed quest unjoinable. Maybe the
  server can let a console in anyway (accept `CircleJoin` after departure, send it what departing players get), if
  the game copes with joining a hunt in progress. Research first (`mhtri-decomp`: what a console does on
  `NtcCircleMatchStart`), then a lab experiment. Rules if it works: joining stays open for the first 10 minutes of
  the quest (arbitrary, to tune), so a protected quest keeps its password hash until then (M3 D9 drops it at
  departure).
- **Blocks keep players apart**: a player can't join a city where someone blocked them, or someone they blocked,
  is; the console gets a neutral error (e.g. "this city is full"), so nobody learns who blocked whom.
- **City search** (`LayerDetailSearch`, `ReqLayerInfo`, then a jump with its match key): once a recording shows the
  menu that sends it (M5 D10).
- **Scripted Dolphin end-to-end tests** (on the lab Mac only: the game image never goes to CI): Dolphin's Pipes
  input backend drives a test profile's Wii Remote from a script (`lab/e2e/<scenario>.sh`), waiting on server
  checkpoints instead of fixed delays (the server's log, or a test-only hook it calls: entered a world server, created
  a city, a quest departed…), a screenshot saved on failure; screenshot pixel checks for the menus before the server
  is involved. Each run starts from a fresh clone of a known profile. Worth it once console scenarios repeat (a
  release check, regressions); a menu path is found once by hand, with screenshots, then scripted.
- **Japanese version (`RMHJ08`)**: the EC/shop check patch (MH3SP's `MHTriCertPatcher.py --patch-ec`), the paid-era
  packets (`ChargeInfo`, `NoCharge` flow), JP string sizes and content blobs, its memory-check addresses.

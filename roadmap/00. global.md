# mh3sp-rs roadmap

A from-scratch Rust server for *Monster Hunter Tri* (Wii) online play, replacing
[MH3SP](https://github.com/sepalani/MH3SP) (Python) in one big-bang migration.
Python MH3SP is the **reference, not the target**: we aim to do better than it, not to copy it.

## Reference policy

- **The game is the hard constraint.** What the console sends and accepts (packet layouts, magic bytes, field
  order, quirks like `FallthroughBug`, timings) must be matched exactly: the game cannot be changed.
  Unknown bytes stay opaque and are reproduced until we understand them.
- **Python's server-side choices are not.** Data model, concurrency, error handling, ID generation, world layout,
  what gets persisted, default texts, bugs and limitations: diverge freely wherever a better design exists.
- **Every divergence on the wire is declared.** When the Rust server deliberately answers differently from
  Python, the difference is recorded in `corpus/divergences.toml` (packet, what differs, why). The replay
  harness accepts declared divergences and fails on undeclared ones, so "different on purpose" never hides
  "different by mistake".
- When Python and the game disagree (a Python bug the game tolerates), the game wins, and the corpus records
  the reason in the divergence entry.

## Goals

- Byte-compatible with the real game (PAL `RMHP08` first, then `RMHE08`, `RMHJ08` later).
- One binary, every server role, `tokio` async.
- Protocol layer separated from game logic, so logic is testable without sockets.
- Built-in NAT negotiation + UDP relay (strategies: `p2p` | `relay` | `hybrid`).
- Deployable as a fleet later (state behind an interface).
- **Fast relays.** Python MH3SP takes ~50 ms (median, up to ~70 ms) to relay a player's town position to another
  player on the same machine (measured from `s04`–`s06`; its stalled reads keep relayed frames waiting for the next
  packet, and the lab ran it with per-packet debug logging). Target: p99 under 2 ms on one host, measured by a
  tier 3 test from M3 on.

## Non-goals (for now)

- Nintendo login (NAS) and GameSpy profile servers: keep using AltWFC or Wiimmfi.
- Offline content tooling (`dump_quest.py`, `dump_trading_post.py`): the JSON they produce is consumed as is.
- Python 2 anything.
- The RFP server: the game never connects to it (verified by capture, see Facts).

## Facts established by live capture (2026-10-08)

Captured with two Dolphin instances against MH3SP `dev` + native AltWFC.

- Login = 6 TCP connections:
  `OPN :8200 (TLS)` → `LMP :8201` (LoginInfo, Ticket, UserList, ServerTime) →
  `LMP :8201` again (UserObject, Ticket, FmpList, FmpInfo ×2) →
  `FMP :8202` staging (time, binaries, `63xx` FmpList, FmpInfo, LayerEnd) →
  `FMP :8202` real session (gates, cities, quests).
- The stage is determined by the port and by `NtcLogin` status (OPN 5, LMP 1 or 2, FMP 3).
- Packet categories are not servers: all 0x61 "Rfp" packets arrive on LMP's port; `ReqRfpConnect` is never sent.
- `ReqCommonKey` is answered with `AnsAuthenticationToken` (skips the encryption step) and the game accepts it.
- **Town and quest gameplay are peer-to-peer UDP (GameSpy GT2).** The server matchmakes and relays the
  connection offer (`NtcLayerBinary2` / `NtcCircleBinary2`, which carry the host `IP:port`), then the consoles do
  GameSpy NAT negotiation (UDP 27901) and talk directly.
- NAT negotiation behind Docker/NAT rewriting hands out unreachable addresses → error 11688 (`0x80030042` in `NtcCollectionLog`).
- P2P traffic, 2 players, lobby + quest start: ~5.5 pkt/s, ~42 B payload, ~0.23 kB/s per direction.
- The PAL game registers with GameSpy as `mh3uswii`.
- The online support code lives in the save's `nocopy/network` file; Capcom ID = server lookup on (support code, slot).
- OPN's second `ReqMemoryCheck` (`0x806311a8` on PAL, `0x806308e8` on US) reads the **NAT negotiation hostname
  compiled into the game** (`natneg1.gs.nintendowifi.net` on an AltWFC-patched disc): that is how the server tells
  which network service the disc was patched for.

## Python MH3SP issues not to reproduce

Found while building the corpus and the replay harness. Each one is a place where the Rust server does better.

- **Stalled reads**: the network loop reads one frame per socket readiness event from a buffered reader
  (`mh/server.py`, `makefile('rb', -1)`), so frames arriving together stay in the buffer until more data comes in.
  The game copes because later traffic unblocks it; answers are still delayed. Rust: read until the buffer is empty.
- **Per-process player ids**: `AnsUserSearchInfoMine`'s two ids (used by the game to tell players apart in relayed
  town packets) come from Python's `hash()`, which is randomly salted per process: they change on every restart.
  Rust: stable ids.
- **No `SO_REUSEADDR`**: a restarted server fails with "Address already in use" until the OS releases the ports.
- **Sessions only in memory**: a server restart drops every session (already addressed by decision 4).
- **Interleaved writes**: `send_packet` writes a frame's header and payload in two `write()` calls, and broadcasts
  write to other players' sockets from other worker threads; the per-connection lock meant for this (`self.rw`) is
  never used. With two players, frames sometimes interleave on the wire (a console then reads garbage such as
  packet id `ff000001`). Rust: one owner per socket, whole frames only.
- **Vanished players linger ~30 s**: a closed socket is only noticed when the next line check fails, so the other
  players see someone who left up to half a minute ago. Rust: react to the closed socket at once, keep the line
  check as a fallback.

## Architecture decisions

1. **Monolith that can route: every node can do everything.** One binary runs every role: `opn`, `lmp`, `fmp`
   TCP listeners and the `natneg` + relay UDP service. Each can be turned on or off in config. A single node is a
   complete server; a fleet is N identical nodes:
   - **Login (OPN, LMP) is stateless** given the database: any node can take any login.
   - **Each world server (Valor1, Beginners1…) is owned by one node.** Gates, cities and quest parties live in that
     node's memory, so town/party broadcasts never leave the process. `AnsFmpInfo` hands the console the owning
     node's address: that is the only "redirect", and the game already does it natively.
   - **Cross-node traffic is rare** (tells and friend requests to a player on another world server, user search,
     population counts, admin announcements): it goes through Valkey pub/sub, used from M3 even on a single node.
   - **Gameplay never touches the fleet** in `p2p` mode; in `relay` mode it goes through the relay of the node that
     ran the NAT negotiation, which needs a public IP without address rewriting.
2. **Three layers, strict direction:**
   - `wire`: framing (`>HHI` size/seq/id header), typed items, `PatData` records, one Rust type per packet.
   - `game`: pure logic, `fn handle(state, session, Request) -> Vec<Effect>` where `Effect` is
     `Reply | SendTo(capcom_id) | Broadcast(scope) | Disconnect`. No sockets, no I/O.
   - `net`: tokio listeners, per-connection task, executes `Effect`s.
3. **Opaque bytes stay opaque.** Unknown fields (`unk_*`, magic constants) are kept as raw values in the
   structs and written back byte for byte. No "cleanups" before the replay harness proves equivalence.
4. **What lives where.** Live state is never shared; summaries are.
   - **Node memory (authoritative):** the live world of the world servers the node owns: gates, cities, circles,
     players, positions. Cities are temporary: if a node dies its consoles' TCP connections die too, so persisting
     them would save nothing. Sharing them would turn every town update into store write + pub/sub + race-prone
     leadership changes.
   - **PostgreSQL (permanent):** accounts (support code + slot → Capcom ID + name), friend lists, blacklists, bans.
   - **Valkey (temporary, shared):** sessions + PAT tickets (TTL), presence (who is online where, TTL),
     population per world server/gate (written by the owning node, read by any node's LMP), cross-node messages
     (pub/sub), world server → node ownership as a lease with TTL (a dead node's world servers get taken over and
     players reconnect there).
   - **Write it once:** no in-process stand-ins to be replaced later. A feature that needs shared temporary data
     uses Valkey from its first line, even on a single node, and therefore no trait with a single implementation.
     Client: `redis` crate (tokio, Valkey-compatible).
5. **Database: PostgreSQL 18 through `sqlx`** (keys `DEFAULT uuidv7()`). Chosen over SQLite (can't be shared by a fleet) and MariaDB (no real
   advantage here). One engine everywhere: dev, CI, prod.
   Migrations with `sqlx migrate` (`migrations/`); compile-time checked queries with the offline cache
   (`cargo sqlx prepare`, `.sqlx/` committed) so CI can build without a live database, while tests use a real one.
   **Schema before 1.0.0**: one file (`migrations/0001_schema.sql`) rewritten in place; a schema change resets the
   database (dev, CI, beta). **From 1.0.0**: forward-only migrations, never edited, no down scripts.
6. **TLS:** `openssl` crate (`tokio-openssl`) with `@SECLEVEL=0`, legacy protocol versions and
   `AES128-SHA`/`AES256-SHA`/RC4/DES ciphers. `rustls` cannot speak to a real Wii (1024-bit CA, TLS ≤ 1.0, RSA key exchange).
7. **Config:** one TOML file. Includes the relay strategy and the external IP handed out to clients.
8. **Logging:** `tracing` + `tracing-subscriber` from the first line of server code. Terminal output first;
   a file (`tracing-appender`) and JSON for production can be added later without touching call sites.
   Filtering with `RUST_LOG` (`EnvFilter`), default `info`. Library crates (`wire`) don't log: they return errors
   and the caller picks the level.

   | Level | Meaning | Examples |
   |---|---|---|
   | `error` | The server is at fault and a human should look, crash or not | Postgres/Valkey unreachable, broken internal invariant (a bug), a listener died |
   | `warn` | Something went wrong and we recovered, or something needs to stand out | malformed packet → connection dropped, unexpected packet for the current stage, P2P failure falling back to relay, every anti-cheat detection or action |
   | `info` | What happens on the server, in player terms | login, Capcom ID chosen, enters gate/city, creates/joins/starts/ends a quest, disconnects; startup/shutdown |
   | `debug` | Protocol flow and decisions, no raw bytes | one line per packet (name, seq, size), state transitions, why a decision was taken (relay strategy), DB/Valkey operations |
   | `trace` | High-volume details | raw packet hexdumps, positions and town relays, cheat-check payloads, P2P/relay datagrams |

   Rules:
   - **Nothing a client does is `error`.** Clients are untrusted: malformed or hostile input is `warn` at most,
     and one `warn` per connection before dropping it, so a hostile client can't flood the logs.
   - **Context lives in spans, not in messages.** One span per connection (`conn` = internal connection number,
     `role`), with `capcom_id` recorded into it once known; nested spans for `world`, `city`, `circle` around the
     code handling them. Field names are fixed across the codebase (`capcom_id`, never `cid` or `user`).
   - **Logs are anonymous: IDs only, at every level.** Never hunter names, IP addresses, chat or friend-request
     text, or anything else typed by or identifying a person. Moderation works by `capcom_id` / support code,
     which the server already holds.
   - **Secrets are never logged, at any level:** PAT tickets (session tokens) and online support codes
     (account credentials in practice). Where one must be correlated, log a short hash.
   - Messages are short and factual (`"joined city"`), the structured fields carry the data.

9. **Health: liveness and readiness are separate.** A small HTTP endpoint (no dependency):
   - `/health/live`: 200 when the runtime answers. This is the container `HEALTHCHECK`
     (`mh3sp healthcheck`, no `curl` in the image); failing it justifies a restart.
   - `/health/ready`: 200 only when Postgres (`SELECT 1`) and Valkey (`PING`) answer within 2 s, else 503 with
     the reason. A dependency outage is **not** a reason to be unhealthy: players already in town or on a quest
     don't need either, a restart would drop them, and both clients reconnect by themselves. Not ready means
     "send no new players here" (load balancer / fleet routing; from M1, OPN also refuses new logins with the
     game's maintenance message).
   - At startup, an unreachable Postgres or Valkey doesn't stop the server: it logs the error, retries in a loop,
     and stays **unhealthy** until both are up (Valkey only when configured), the migrations have run and it has
     become ready once (nobody can be connected yet, so a restart loses nothing). After that, an outage only makes
     it not ready, logged at `error` for either dependency (players can't join). (Decided in M1; M0's skeleton
     still exits at startup.)

## Dev environment

- `scripts/dev.sh`: starts the dependencies below and creates/completes `.env` (idempotent).
- `scripts/ci-tests.sh [--docker | --woodpecker]`: runs exactly what CI runs (natively, in the CI image, or the
  real pipeline files through `woodpecker-cli exec`, services included).
- `docker compose up -d --wait`: PostgreSQL 18 on `localhost:55432`
  (`DATABASE_URL=postgres://mh3sp:mh3sp@localhost:55432/mh3sp`) and Valkey 8 on `localhost:56379`
  (`VALKEY_URL=redis://localhost:56379`). Shifted ports avoid clashing with local instances.
- The server runs with `cargo run -p server` (reads `config.toml`, created by `dev.sh`); migrations run at
  startup. It needs ports 8200–8202, like Python MH3SP: stop one to run the other (`tools/oracle.sh` restarts
  Python when a replay needs it).
- `Dockerfile`: the release image (Debian slim + OpenSSL 3, non-root, `HEALTHCHECK` on `/health/live`).
- Game side: the lab in `../mh3sp/lab` (Dolphin profiles, hosts toggle, native AltWFC, Python MH3SP as oracle).
- Deliberately not in compose: AltWFC / NAT negotiation (Docker port mapping rewrites client addresses → P2P fails).
  Python MH3SP may join compose later for tier 4 (TCP only, no such problem).

## Testing strategy

Python MH3SP is the reference (see Reference policy). An undeclared diff against it is a finding, not a
nuisance: either reverse-engineering knowledge the port would otherwise lose, or a divergence to declare.

**Corpus.** Scenarios played in the lab against Python MH3SP and recorded from **Dolphin's network captures**
(`DumpAsPCAP` + SSL dumps): every TCP connection separately, both directions, timestamps, OPN's TLS already
decrypted, plus the UDP traffic (NAT negotiation, P2P). Imported into `corpus/<scenario>/`. Volatile fields
(tickets, support codes, Capcom IDs, timestamps) are found by recording a scenario twice and masked per packet type.
Details in `M0 foundations.md`.

| Tier | What | Runs where | Since |
|---|---|---|---|
| 1. Unit | `wire` round-trips (`decode(encode(x)) == x`, `encode(decode(bytes)) == bytes` on every corpus packet), property tests on items/`PatData`; `game` logic as pure functions (`Request` → `Effect`s) | CI, every push | M0 |
| 2. Replay | Each recorded scenario's client packets replayed over real sockets against a server; replies diffed against the corpus. Validated first against Python MH3SP | CI, every push | M0 |
| 3. Scripted E2E | Fake consoles (Rust test client crate) over real sockets: TLS on OPN, the full 6-connection login, multi-client scenarios (2–4 clients in a city/quest), disconnects mid-flow, concurrency stress | CI, every push | M1 |
| 4. Live differential | The same scripted scenarios against Python MH3SP **and** Rust, started side by side in CI; diff the conversations | CI, nightly + on demand | M1 |
| 5. NAT negotiation / relay | Fake UDP peers run NAT negotiation and exchange traffic in `p2p`, `relay`, `hybrid`; simulated NAT (address/port rewriting) and forced failures for the hybrid fallback | CI, every push | M4 |
| 6. Dolphin E2E | Real game in Dolphin, automated: launch with `play.sh`-style config, drive menus, assert progress from server logs and game memory (error code via the PAL symbol maps), screenshots on failure | Self-hosted runner only (needs the game image), nightly / manual | Spike in M1, scenarios from M2 |

### CI: self-hosted Gitea + Woodpecker

- Pushes to Gitea trigger Woodpecker pipelines (`.woodpecker/*.yml`).
- Secrets available to pipelines: `gitea_user`, `gitea_token` (Gitea registries: Cargo, npm, container).
- `push` pipeline: `fmt`, `clippy -D warnings`, tiers 1–3 and 5, coverage report on tiers 1–3.
  `postgres:18` and `valkey/valkey:8` Woodpecker services for tests (each test gets its own database via `#[sqlx::test]`);
  `SQLX_OFFLINE=true` for the build, plus a check that `.sqlx/` is up to date.
  Cache `~/.cargo` and `target/` between runs.
- `nightly` pipeline (Woodpecker cron): tier 4, with Python 3 + a pinned MH3SP checkout.
- `dolphin` pipeline: tier 6 on a Woodpecker agent running on the Mac (local backend, own label), because the
  game image never leaves that machine. Manual or nightly trigger.
- `release` pipeline (on tag): container image built with `woodpeckerci/plugin-docker-buildx:5.0.0` (allowed as a
  privileged plugin) and pushed to the Gitea container registry. The image must run with host networking (or a
  public IP without address rewriting) whenever NAT negotiation is enabled.
- The Cargo registry is only needed if crates get shared between repos (e.g. the test client); not before.

### M3 — Multiplayer
- [ ] Broadcast scopes: layer (gate/city), circle (in-process: same owner node); `SendTo(capcom_id)` via Valkey pub/sub when the recipient may be elsewhere.
- [ ] City join: `LayerHost`, `NtcLayerIn/Out`, `NtcLayerUserPosition`, `NtcLayerBinary`, `NtcLayerBinary2` (directed).
- [ ] Circle join/leave/kick/break, host transfer, `NtcCircleBinary(2)`, list-change notifications.
- [ ] Leader transfer on disconnect (city and circle).
- [ ] Chat (layer, tell), friends (add/accept/delete/list), blacklist.
- [ ] Hunter profile block (`ReqUserBinarySet`, 256 bytes; held in memory since M2). The server forwards it to other
      consoles, which parse it to draw the hunter: a crafted block is a risk to **other players' games**, before
      being a cheating problem. In stages:
      1. parse and validate the known fields (only 2 of 256 bytes are known: HR u16 @0, weapon type u8 @5); an
         invalid update is rejected (previous profile kept and forwarded, `warn`, anti-cheat flag in M6). The
         **database only ever stores parsed, validated fields** (`hunter_profiles`), never the raw block. The raw
         block lives only in memory while its player is connected, because other consoles need all 256 bytes to
         draw the hunter and unknown bytes can't be rebuilt yet; the console resends it at every login anyway;
      2. map the rest field by field (recordings of different hunters and gear, `mhtri-decomp`, MH3SP's equipment
         ids), tightening validation each time;
      3. once fully mapped, rebuild the block from validated fields before forwarding: whatever another console
         receives is then well-formed by construction, and the raw bytes leave memory too. Switch only when the
         rebuilt block equals the original, byte for byte, for every profile in the corpus (a profile that doesn't
         round-trip means a field isn't really mapped yet).
- [ ] Concurrency model written down: which task owns which state, no cross-task socket writes without channels.

- [ ] Tier 3 scenarios with 2–4 clients: join/leave, host transfer, chat, friends; disconnect at every step; a stress test (many clients, random actions) to shake out races.

- [ ] Tier 3 relay-latency test: clients relaying positions through one city, p99 under 2 ms on one host.

**Done when:** two consoles in one city, both in the same quest, with AltWFC still doing NAT negotiation; multi-client tier 3 green.

### M6 — Anti-cheat (research)

What the server can and cannot see:

| Data | Path | Server can check? |
|---|---|---|
| Hunter profile (HR, gear, stats) | `ReqUserBinarySet`, `HunterSettings` on every layer change | **Yes**: sanity rules (HR range, valid item/equipment IDs, possible combinations) |
| Game's own cheat report | `NtcCheatCheck` (`60801000`, "send cheat check data"), sent after every layer change, currently ignored | **Yes, once decoded**: Capcom's built-in anti-cheat signal |
| Game memory | `ReqMemoryCheck` (`60810100`): the server asks for N bytes at an address | **Yes**: hash code regions to detect Gecko/AR codes; random sampling over a session |
| Town positions | `NtcLayerUserPosition`, relayed through the server | **Partly**: speed/teleport checks, once the format is decoded |
| Quest combat (moves, damage, HP) | P2P UDP between consoles | **No** in `p2p` mode. In `relay` mode the traffic passes through us, but GT2 + game messages would need decoding, and validating damage means simulating game rules |
| Quest results / rewards | Mostly local to the save | **Barely**: quest duration from circle start/end, at best |

Plan:
- [ ] Decode `NtcCheatCheck` (decomp + corpus) and log it; then act on it.
- [ ] Memory-check sampling: known-good hashes of code regions per region/version; mismatch → flag.
- [ ] Profile sanity rules.
- [ ] Moderation tooling: flags, bans by support code / Capcom ID.
- [ ] Research only: decode GT2 in relay mode, position/speed heuristics.

Limits: the client is fully under the player's control. A cheat can fake `NtcCheatCheck` and memory-check answers.
The realistic goal is to stop casual cheats (Gecko codes, edited saves) and give moderators evidence, not perfect integrity.

## Traps to remember

- Legacy TLS (see decision 6). Test against real-Wii settings, not only Dolphin.
- Reproduce unknown bytes exactly; MH3SP has many `# TODO: Field??` constants that the game depends on.
- Copy timings: the ~1.5 s connection delay, 30 s line check, client timeouts.
- `str` vs `bytes` is mixed in MH3SP for Capcom IDs and names: decide each field's real type from the corpus.
- The external IP handed out in `AnsLmpConnect` / `AnsFmpInfo` must be reachable by clients (config, not `0.0.0.0` guessing).
- NAT negotiation must see real client addresses: never behind Docker port mapping or a NAT-rewriting load balancer.
- The game never retries P2P by itself: every fallback costs the player one failed attempt.

### M7 — Admin website

A website for the people running the server, on top of M5's admin API.
- [ ] Live view: world servers, gates, cities, quests (with their players and states), who is online and where.
      Data: each node's admin API for its own world servers, Valkey summaries (population, presence) for the fleet
      view.
- [ ] Hunter pages: profile (HR, weapon, gear decoded from the profile block), friends list, managed from the site
      (the game fetches its friend list from the server, so changes show up in game).
- [ ] Moderation: kick, ban (by Capcom ID / support code), the whitelist (MH3SP's `event-quest-rotation-full`
      idea), broadcast announcements.
- [ ] Anti-cheat review (M6): flagged players with their evidence (cheat-check data, memory-check mismatches).
- [ ] Self-service access (`access = on_register | admin`), preferred flow: a console that isn't allowed is refused with a message such as
      "Register on https://… and enter the code K7QM-2XPA"; the player, signed in on the site (email + password),
      enters it under "add a console", which links that console to their account and whitelists it.
      - The code is a short one-time pairing code kept in Valkey with an expiry, pointing to the console; the
        support code itself never leaves the server, the website only links the console the pairing code points to.
      - Not by typing the support code on the site, even if the game shows it in a menu (to check): codes seen in
        screenshots or streams would let anyone claim someone else's console first. The pairing code shown by the
        server proves the person holds the console right now.
      - A first-time console has no support code at OPN yet: it goes through to LMP, gets its support code in
        `AnsLoginInfo`, and is refused right there; afterwards it is refused at OPN until registered.
      - To verify in the game first: that a refusal at LMP (`NtcShut` with a text) shows its message, and that the
        console keeps the support code it was just issued.
      Other ideas considered:
      - **Code shown in game**: a console that isn't whitelisted gets a short one-time code in a login message
        (the server already writes the texts of `AnsAnnounce` / maintenance / no-charge screens); the player types it
        on the website to register that console. Nothing to install, and it proves they own the console.
      - **Support code typed on the site**: if the game shows the online support code somewhere in its menus
        (to check), players paste it on the site. Simpler, but anyone could register someone else's code.
      - **Sign-in on the site** (e.g. Discord, where the community already is), so each registration belongs to an
        account that admins can contact or ban.
- [ ] Event content: quest definitions, rotation and trading post, edited from the site (they live in PostgreSQL
      since M2); a change reaches every node through Valkey and every console through the binary version.
- [ ] Rotation calendar: schedule which event/arena quests are live when, including the **Jhen Mohran** event
      (MH3SP computes its windows in `mh/time_utils.py`), with a preview of what players see at a given date.
- [ ] Health and metrics per node, pulled live from each node listed in the fleet registry (`/health/ready`, a
      `/metrics` endpoint: players, relay latency, …). History, if wanted, in a metrics system (e.g. Prometheus +
      Grafana), not in the game database.
- [ ] Admin accounts with authentication; every moderation action logged (who did what, when).
- Privacy follows the logging rules: the site shows Capcom IDs and hunter names to admins (moderation needs them),
  never IP addresses; support codes are masked.
- Stack decided when M7 starts (the Gitea npm registry and the Docker image pipeline are available).

## Fleet: not planned

A single server is expected to be enough (hundreds of players; gameplay is P2P). Nothing is built for a fleet:
no ownership leases, no node registry, no cross-node messages. Designs only avoid making one impossible: world
servers identified by name, state behind small interfaces, the cache's data temporary. If a fleet is ever
wanted: shared cache (Valkey), world-server ownership with leases, a node registry, cross-node messages, and
multi-node tier 3 tests.

## Deployment shapes

- **Standalone** (the default): the server and PostgreSQL (plus AltWFC until our own Nintendo login), `access =
  open`. The server never depends on the website.
- **With the website**: adds accounts, pairing and the `on_register` / `admin` access modes, and the admin pages.
  Those access modes without a website are a startup `error` (nobody could ever register).

# M1 — Database schema (draft for review)

**Status: settled (2026-10-08).** The SQL lives in [`migrations/0001_schema.sql`](../migrations/0001_schema.sql), applied by
the server at startup and checked against SQLite 3.51 (constraints exercised by hand: Capcom ID format, slot range,
HMAC and public id lengths, disc ids, key formats, foreign keys and cascades, STRICT types, terms versions starting
at 2). Rewritten in place
until 1.0.0 (`scripts/dev.sh --reset` after a change). This document keeps the reasoning; the file is the truth.

Inputs: decisions D1–D7, support code storage, identity (`M1 login funnel.md`).

## Principles

- **SQLite** (bundled with the server), one file, WAL mode (a website on the same machine shares it), foreign keys
  enabled on every connection, `STRICT` tables.
- **Keys**: every table has an internal `INTEGER PRIMARY KEY`, used by foreign keys. Entities that people reference
  (website URLs, API, logs) also have a `public_id`: a UUID v7 generated by the server, stored as 16 bytes.
  **No internal key ever leaves the database.** Exceptions, later: `settings` (keyed by name) and the audit log (UUID
  primary key, append-only). UUIDs stop enumeration; authorization checks on every request still decide who may
  see or change what.
- **No enum types** (SQLite has none anyway): enumerations are `TEXT` with a `CHECK`; formats are checked with `GLOB`
  (SQLite has no regular expressions by default).
- **No history**: rows are overwritten in place (terms excepted: each version is a row, see `terms`).
- **Settings are configuration until the website**: the accepted NAT hostname is an environment variable; access modes
  and registration come with the website (M8, a `settings` table), until then access is open.
- **Texts are a dictionary in the code**: `text(Text, Language)`, a `match` with every key's English text, so a
  missing text is a compile error. Overrides and translations come with the website (M8, a `texts` table) by
  changing only that function's body.
  **Terms** are already overridable (`terms` table) because the console's terms version must change when they do.
- **Only permanent data.** Sessions, tickets, pairing codes, presence, populations and live worlds (gates, cities,
  quests in progress) are in the server's memory.
- **No secrets in clear**: support codes are stored as HMAC-SHA256(pepper, code), 32 bytes; the pepper is the
  `SECRET` environment variable and never changes.
- **Game bytes stay bytes**: hunter names are `BLOB` (the game may use Shift-JIS); identifiers the game formats
  (`0-9A-Z`) are `TEXT` with a `CHECK`.
- Timestamps: UTC text, `CURRENT_TIMESTAMP` by default.
- Names: plural tables, `snake_case`, foreign keys `<entity>_id`.

## M1 tables

The SQL is in `migrations/0001_schema.sql`. Per table, what it holds and why:

| Table | One row per | Notes |
|---|---|---|
| `terms` | edit of the terms or sub-terms × language | the `AUTOINCREMENT` key is the version sent to the console (u32): built-in terms are version 1, overrides start at 2, and ids are never reused (plain SQLite keys can be, after a deletion), so edited terms are always re-shown |
| `consoles` | console | `support_code_hmac` (HMAC-SHA256 with the pepper, never the code), disc region, first/last seen |
| `hunters` | Capcom ID slot | an online identity a save hunter plays under; a new name on the slot means another hunter: name and profile overwritten, social links dropped, Capcom ID and moderation records kept; no history |

Not in the database: **world servers** (the 12 of MH3SP: names, types, capacity), **server types** (HR limits) and
the **world layout** (40 gates × 100 players, 40 cities × 4 per gate). They are game constants in the code,
not overridable. A world server is identified by its name (`Valor1`) in logs and presence.

## Answered

1. A Capcom ID slot is an online identity. Another hunter taking it (a new name) overwrites name and profile and
   drops its social links; the Capcom ID and its moderation records stay, so switching hunters can't clean a
   record. (To check: whether the game can delete a Capcom ID.)
2. `last_seen_at`: kept (consoles and hunters).
3. Region: on the console.
4. Texts: a dictionary in the code only, until the website (M8) brings the `texts` override table back. Terms in
   their own table, the key being the version (built-in = 1, overrides from 2).
5. World servers: built-in constants, identified by name; not in the
   database. Same for server types and the world layout.
6. Access: open until the website (M8) brings the `settings` table with `access` (open / on_register / admin) and
   `registration` (open/closed). The server never depends on the website (standalone: server + database, `access = open`).
7. Enumerations: `text` with a `CHECK`.
8. SQLite (one file, WAL; a website shares it on the same machine); public ids are UUID v7 generated by the server.
9. Keys: internal `INTEGER PRIMARY KEY` everywhere (except `settings` and the audit log), `public_id` UUID on what
   people reference; internal keys never leave the database.

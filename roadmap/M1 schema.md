# M1 — Database schema (draft for review)

**Status: draft, to challenge.** Becomes `migrations/0001_schema.sql` once settled (rewritten in place until
1.0.0, see the schema policy in `M1 login funnel.md`).

Inputs: decisions D1–D7, V1–V4, support code storage, identity (`M1 login funnel.md`).

## Principles

- **PostgreSQL 17.** Keys are **UUID v7**, generated by the server (the `uuid` crate): Postgres 17 has no built-in
  v7 generator (Postgres 18 does: `uuidv7()`, a reason to consider upgrading the image).
- **Only permanent data.** Sessions, tickets, pairing codes, presence, populations, ownership leases and the fleet
  registry are in the cache (V1). Live worlds (gates, cities, quests in progress) are in node memory.
- **No secrets in clear**: support codes are stored as HMAC-SHA256(pepper, code), 32 bytes; the pepper comes from
  the environment and never changes.
- **Game bytes stay bytes**: hunter names are `bytea` (the game may use Shift-JIS); identifiers the game formats
  (`0-9A-Z`) are `text` with a `CHECK`.
- `timestamptz` everywhere; `created_at` defaults to `now()`.
- Names: plural tables, `snake_case`, foreign keys `<entity>_id`.

## M1 tables

```sql
-- Key/value settings, readable by every node; editable by admins (website, M7).
-- Known keys: 'natneg_hostname' (the only accepted NAT negotiation hostname, D3).
CREATE TABLE settings (
    key         varchar(32) PRIMARY KEY,
    value       text        NOT NULL,
    updated_at  timestamptz NOT NULL DEFAULT now()
);

-- Every text the server sends (D1, D6): terms, sub-terms, announce, no-charge, refusal and kick messages,
-- vulgarity lists, and the server type names/descriptions shown in the server list.
-- Lookup: (key, console language), falling back to 'en'.
CREATE TABLE texts (
    key         varchar(64) NOT NULL,          -- e.g. 'terms', 'refusal.not_ready', 'server_type.rookie.name'
    language    varchar(8)  NOT NULL,          -- ISO 639-1 ('en', 'fr', 'de', …), mapped from the game's code
    value       text        NOT NULL,          -- in the game's markup (<BR>, <CENTER>, <SIZE=n>, <C=n>, <END>)
    version     integer     NOT NULL DEFAULT 1, -- bumped on every edit: the console re-shows the terms
                                                -- only when their version changes
    updated_at  timestamptz NOT NULL DEFAULT now(),
    PRIMARY KEY (key, language)
);

-- The four server types of the game (fixed by the game's content), with their HR limits.
CREATE TYPE server_type AS ENUM ('open', 'rookie', 'expert', 'recruiting');

CREATE TABLE server_types (
    type        server_type PRIMARY KEY,
    hr_min      smallint NOT NULL CHECK (hr_min BETWEEN 0 AND 999),
    hr_max      smallint NOT NULL CHECK (hr_max BETWEEN hr_min AND 999)
);

-- World servers shown in the server list (D2). Gates and cities are generated from the counts.
CREATE TABLE world_servers (
    id              uuid        PRIMARY KEY,
    position        smallint    NOT NULL UNIQUE,   -- order in the list; the game addresses servers by index
    name            text        NOT NULL UNIQUE,   -- e.g. 'Valor1'; max length to check against FmpListData
    type            server_type NOT NULL REFERENCES server_types,
    capacity        integer     NOT NULL DEFAULT 2000 CHECK (capacity > 0),
    gate_count      smallint    NOT NULL DEFAULT 40 CHECK (gate_count BETWEEN 1 AND 40),
    gate_capacity   integer     NOT NULL DEFAULT 100 CHECK (gate_capacity > 0),
    city_count      smallint    NOT NULL DEFAULT 40 CHECK (city_count BETWEEN 1 AND 40),
    enabled         boolean     NOT NULL DEFAULT true,
    created_at      timestamptz NOT NULL DEFAULT now()
);

-- A console, identified by its online support code (never stored in clear).
CREATE TABLE consoles (
    id                  uuid        PRIMARY KEY,
    support_code_hmac   bytea       NOT NULL UNIQUE CHECK (length(support_code_hmac) = 32),
    region              varchar(8)  NOT NULL,       -- disc id: 'RMHP08', 'RMHE08' (D3)
    created_at          timestamptz NOT NULL DEFAULT now(),
    last_seen_at        timestamptz NOT NULL DEFAULT now()
);

-- A hunter: one of the console's 6 Capcom ID slots.
CREATE TABLE hunters (
    id              uuid        PRIMARY KEY,
    console_id      uuid        NOT NULL REFERENCES consoles ON DELETE CASCADE,
    slot            smallint    NOT NULL CHECK (slot BETWEEN 1 AND 6),
    capcom_id       text        NOT NULL UNIQUE CHECK (capcom_id ~ '^[0-9A-Z]{6}$'),
    name            bytea       NOT NULL,           -- as the game sends it
    created_at      timestamptz NOT NULL DEFAULT now(),
    last_seen_at    timestamptz NOT NULL DEFAULT now(),
    UNIQUE (console_id, slot)
);
```

Seed data (in the same file, `INSERT … ON CONFLICT DO NOTHING`):
- `server_types`: open 0–999, rookie 0–30, expert 31–999, recruiting 0–999 (MH3SP's values).
- `world_servers`: Valor1–4 (open), Beginners1–2 (rookie), Veterans1–2 (expert), Greed1–4 (recruiting), with ids
  fixed in the seed so every node and every reset agrees.
- `texts`: English defaults for every key; server type names and descriptions from MH3SP.
- `settings`: no default `natneg_hostname`: it is derived from the deployment's domain (our patch, D3), so a fresh
  install without it refuses every disc with a clear "server not configured" log line.

## Questions to challenge

1. **Hunter deletion**: the game can overwrite a slot. Delete the row and create a new hunter (new Capcom ID), or
   keep the old row (history, friends pointing at it) and mark it replaced?
2. **`last_seen_at`**: updated on every login (one write per login), useful for the website and cleanup; or dropped
   until something needs it?
3. **Region on the console or on the hunter**: a console has one disc region in practice; a save could move
   between consoles, though. Keep it on `consoles`?
4. **Texts versioning**: a `version` per (key, language) only matters for the terms; keep it generic, or move the
   terms to their own table?
5. **World servers by `position`**: the game refers to servers by index in the list. Renumbering reshuffles which
   server players see where; is `position` enough, or should ids be the stable reference everywhere and position
   only a display order?
6. **Whitelist shape** (later, but it changes `consoles`): linked-to-an-account = whitelisted, or an explicit table?
7. **Enum vs table for server types**: an enum is tight but changing it needs a schema change; a plain text key
   with a `CHECK` is easier to evolve. Either is fine pre-1.0.
8. **Postgres 18** for `uuidv7()` as a column default, or keep generating ids in the server?
